As there will be many class and objects -> which principles to follow for easy management of all this complicated relation and entities.
like try to make less tightly coupled. -> as will make it complex to add new features.
### Problems
- maintainability -> like application easy to integrate new feature
- readability -> new team need to understand what is code is doing.
- bugs -> resolve bugs should be easy 
someone(`Robert C Marta`) has made this SOLID principles which if followed it will be easy to fix all problems.
## SOLID
S -> Single responsibility principle(`SRP`)
O -> open close principle (`OCP`)
L -> List of substitution principle (`LSP`)
I -> Interface segregation principle (`ISP`)
D -> Dependency inversion principle (`DIP`)
### `SRP`
Single responsibility principle says
- A class should have only one reason to change
- A class should do only 1 thing
1 class = 1 responsibility.
example : TV remote should control only TV(not all appliance).
all it's attribute and methods together do only 1 responsibility.
example : product and cart. 
![[Pasted image 20260914130800.png]] here, `1..*` means one to many relation.
here, shopping cart is breaking `SRP`.
there, are multiple reason when code in this class will be change -> breaks single responsibility.
solve -> ![[Pasted image 20260914154827.png]]
now each class have single responsibility.

#include <vector>

using namespace std;

// Product class representing any item of any ECommerce.
class Product {
public:
    string name;
    double price;

    Product(string name, double price) {
        this->name = name;
        this->price = price;
    }
};

// Violating SRP: ShoppingCart is handling multiple responsibilities
class ShoppingCart {
private:
    vector<Product*> products; // has-a

public:
    void addProduct(Product* p) {
        products.push_back(p);
    }

    const vector<Product*>& getProducts() {
        return products;
    }
    // 1. Calculates total price in cart.
    double calculateTotal() {
        double total = 0;
        for (auto p : products) {
            total += p->price;
        }
        return total;
    }

    // 2. Violating SRP - Prints invoice (Should be in a separate class)
    void printInvoice() {
        cout << "Shopping Cart Invoice:\n";
        for (auto p : products) {
            cout << p->name << " - $" << p->price << endl;
        }
        cout << "Total: $" << calculateTotal() << endl;
    }

    // 3. Violating SRP - Saves to DB (Should be in a separate class)
    void saveToDatabase() {
        cout << "Saving shopping cart to database..." << endl;
    }
};

int main() {
    ShoppingCart* cart = new ShoppingCart();

    cart->addProduct(new Product("Laptop", 1500));
    cart->addProduct(new Product("Mouse", 50));

    cart->printInvoice();
    cart->saveToDatabase();

    return 0;
}

### `OCP`
Open close principal says,
- A class should be open for extension but close for modification(changes in old code).
- old code should not be touched to add new features.
for above example : ![[Pasted image 20260914161632.png]]
now need feature -> need to store same data in MongoDB, file.
to follow `OCP` -> can't just add this two new method in `DBstorage`.
Can do it using Abstraction + Inheritance + polymorphism.
make `DBStorage` as interface/abstract class and make it's many implementations.(It give what can be done without saying how it is done -> ![[Pasted image 20260914162640.png]])
all methods declared not implemented.
`save()` -> have save to SQL,MongoDB and file as implementation.
abstraction : making abstract class
inheritance : to make child of abstract class
polymorphism : variable of parent class type can hold value of child class.
![[Pasted image 20260914163657.png]]
now if adding any more feature need to give one more implementation -> solved `OCP`.

### `LSP`
Liskov Substitution principle, says
- Sub-classes should be substitute-able for their base classes.
if class A(Base class) and B(sub class), a client need A then, client should be able to work with B also.![[Pasted image 20260915182624.png]]
for Base class -> can put child class.
in other words, sub-class should only expand on base class never narrow it.
![[Pasted image 20260915183248.png]]
A and B follows LSP.
this is simple but, mostly it is broken by overriding.
example:
interface account -> has 2 features `deposit()` and `withdraw()`.
saving and current account are implementation.
![[Pasted image 20260915184002.png]]
client interacts with interface.
now, new type of account `FixedDeposit` but it can't withdraw that breaks `LSP`(`FixedDeposit` is not substitute-able for account).
override withdraw -> will throw exception![[Pasted image 20260915184506.png]]
to solve it 
- Bad approach => change client code to have if condition if account if FD then, don't withdraw ![[Pasted image 20260915185051.png]] -> ![[Pasted image 20260915185132.png]] Problem is client is tightly coupled with accounts implementation.(Thus, breaks `OCP` if new client then, every client code needs to be changed) 
- Proper Fix => Fixed Deposit class should not be child of account, if he wants to be child must implement all method of parent correctly. make `NonWithdrawableAccount` interface and `WithdrawableAccount`.![[Pasted image 20260915190036.png]] now client has list of `NonWithdrawableAccount` and `WithdrawableAccount` so, client don't break `OCP`.![[Pasted image 20260915190852.png]]

#include <iostream>
#include <vector>
#include <typeinfo>
#include <stdexcept>

using namespace std;


class DepositOnlyAccount {
public:
    virtual void deposit(double amount) = 0;
};

class WithdrawableAccount : public DepositOnlyAccount {
public:
    virtual void withdraw(double amount) = 0;
};

class SavingAccount : public WithdrawableAccount {
private:
    double balance;

public:
    SavingAccount() { 
        balance = 0; 
    }

    void deposit(double amount) {
        balance += amount;
        cout << "Deposited: " << amount << " in Savings Account. New Balance: " << balance << endl;
    }

    void withdraw(double amount) {
        if (balance >= amount) {
            balance -= amount;
            cout << "Withdrawn: " << amount << " from Savings Account. New Balance: " << balance << endl;
        } else {
            cout << "Insufficient funds in Savings Account!\n";
        }
    }
};

class CurrentAccount : public WithdrawableAccount {
    private:
        double balance;
    
    public:
        CurrentAccount() { 
            balance = 0; 
        }
    
        void deposit(double amount) {
            balance += amount;
            cout << "Deposited: " << amount << " in Current Account. New Balance: " << balance << endl;
        }
    
        void withdraw(double amount) {
            if (balance >= amount) {
                balance -= amount;
                cout << "Withdrawn: " << amount << " from Current Account. New Balance: " << balance << endl;
            } else {
                cout << "Insufficient funds in Current Account!\n";
            }
        }
    };

class FixedTermAccount : public DepositOnlyAccount {
private:
    double balance;

public:
    FixedTermAccount() { 
        balance = 0; 
    }

    void deposit(double amount) {
        balance += amount;
        cout << "Deposited: " << amount << " in Fixed Term Account. New Balance: " << balance << endl;
    }
};

class BankClient {
private:
    vector<WithdrawableAccount*> withdrawableAccounts;
    vector<DepositOnlyAccount*> depositOnlyAccounts;

public:
    BankClient( vector<WithdrawableAccount*> withdrawableAccounts, 
        vector<DepositOnlyAccount*> depositOnlyAccounts) { 
        this->withdrawableAccounts = withdrawableAccounts; 
        this->depositOnlyAccounts = depositOnlyAccounts;
    }

    void processTransactions() {
        for (WithdrawableAccount* acc : withdrawableAccounts) {
            acc->deposit(1000);
            acc->withdraw(500); 
        }
        for (DepositOnlyAccount* acc : depositOnlyAccounts) {
            acc->deposit(5000);
        }
    }
};

int main() {
    vector<WithdrawableAccount*> withdrawableAccounts;
    withdrawableAccounts.push_back(new SavingAccount());
    withdrawableAccounts.push_back(new CurrentAccount());

    vector<DepositOnlyAccount*> depositOnlyAccounts;
    depositOnlyAccounts.push_back(new FixedTermAccount());

    BankClient* client = new BankClient (withdrawableAccounts, depositOnlyAccounts);
    client->processTransactions();

    return 0;
}
