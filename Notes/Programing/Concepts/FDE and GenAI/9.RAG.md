This is called as RAG mode => retrieval(similarity content fetched) augmentation(give only relevant context to the LLM) generation(LLM generates response) => RAG.
#### RAG concept
This is RAG => it uses vector to give LLM only the necessary context instead of giving all of it for a particular query.
basic concept is give only the needed context to answer the query.
in vector DB also when search will use `IVF` or `HNSM` => fast search in the context and give only relevant context.
#### Convert PDF to vector
can't make 1 vector of 1 PDF => as it will lost semantic.
need to be able to cherry pick some part of all PDF which is relevant to our query in hand.
take first 1000 words and make vector.
1 document = many(100) vectors.
![[Pasted image 20261018123944.png]]
will use Vector DB => `Pinecone`.
thus, now LLM has long term memory and RAG will help to retrieve only the relevant context(using vector embedding and comparison) from the history instead of full context.
long term memory as history and vectors in DB.

```java
    private final VectorStore vectorStore;
    private final ChatClient chatClient;

    @Value("classpath*:knowledge/*.pdf")
    private Resource[] policyFiles;

    public ChatbotService(VectorStore vectorStore, ChatClient.Builder chatClientBuilder) {
        this.vectorStore = vectorStore;
        this.chatClient = chatClientBuilder.build();
    }

    @PostConstruct // run on start-up
    public void loadKnowledgeBase() {
        // 1. Read all PDF files.
        // 2. FOr each file I will divide them into chunks
        // 3. I will store those chunks in vector DB --> Pinecone.

        List<Document> allChunks = new ArrayList<>();

        TokenTextSplitter splitter = TokenTextSplitter.builder()
                .withChunkSize(300)
                .build();

        // Loop through each PDF file
        for (Resource resource : policyFiles) {

            PagePdfDocumentReader reader = new PagePdfDocumentReader(resource);
            List<Document> pages = reader.read();
            List<Document> chunks = splitter.apply(pages);
            allChunks.addAll(chunks);
        }
        vectorStore.add(allChunks);
    }
```

```java
    public String answerUserQuery(String question) {
        // 1. Question --> vector
        //2. similrity search in our vector db
        //3. top 4 results fetch

        List<Document> relevantChunks = vectorStore.similaritySearch(
                        SearchRequest.builder()
                                .query(question)
                                .topK(4)
                                .build()
                );// langchain pipeline similifies RAG => it gives context => vector and meta data is store so it retrived

        StringBuilder context = new StringBuilder();

        for (Document document : relevantChunks) {

            context.append(document.getText())
                    .append("\n\n");
        }

        String finalContext = context.toString();

        String prompt = """
                You are an AI customer support assistant for our e-commerce company.

                Answer the customer using ONLY the company information provided below.

                If the answer is not available in the provided information, say:
                "I don't have that information in the company documents."
                
                COMPANMY INFORMATION
                %s
                
                """.formatted(finalContext);

        return chatClient.prompt()
                .system(prompt) // high priority(avoid prompt injection) 
                .user(question) // 
                .call()
                .content();
    }
```

## Chucking
divide a big document into chunks and make vectors of this chunks.
vector = numerical representation of words.
thus, can't make vector of big document. => as need to capture semantic meaning.
###### Type of chunking
- Fixed size chunking 
	- problem might cut statement in 2 part![[Pasted image 20261019102108.png]]
	- thus, full context is lost
	- Solved: by using overlapping => reduces change of overlapping ![[Pasted image 20261019102234.png]]
	- problem: hard to decide how much overlapping and chunk size 
		- generic rule ![[Pasted image 20261019102351.png]]
- Structural Chunking
	- document is structure => title, heading, articles, ![[Pasted image 20261019102520.png]]
	- do chunking based on the structure of document => no need to overlap
	- decide chunking based on => title, sub-heading, paragraphs, section, tables, etc
	- It is also called a document aware chunking.
	- Problem: if document is raw => Semantic Chunking
- Semantic Chunking
	- it is for document which are not structure and are in the raw form ![[Pasted image 20261019103012.png]]
	- has 2 semantic context => ![[Pasted image 20261019103100.png]] it has return policy and shipping 
	- Step 1: divide small lines in chucks => chuck after line break![[Pasted image 20261019103414.png]]
	- Step 2: make vector of all this lines ![[Pasted image 20261019103458.png]]
	- Step 3: can't store in DB as too much data and also context is scattered or will hallucinate.
	  thus, vector in series find cosine similarity of adjutant vectors.![[Pasted image 20261019103852.png]]
	  now, can know similarity sentence and join all similar to make those 2 vector ![[Pasted image 20261019103926.png]]
	- This is time consuming process but, will not need overlap. => trade off between relationship quality and time.
now by advance chunking now have only better vectors.

## Ranking document 
if user query gives some top 5 results
![[Pasted image 20261020183321.png]]
retrieval works as correct document.
as 4th should have been at 1st => as damaged policy is more important.
Solved by using Re-ranking.
Problem with Normal ranking
- Document and query embedded separately(independently) => thus, ranking will be improper.
- can't analyse together => analyse query and one document at a time.
this together is called as re-ranking model => Cross encoder model.
![[Pasted image 20261020184354.png]]
relevance score shows how much related this query and document are.
change the flow => retrieve many document and then, do a re-ranking using re-ranking model => from it get top 3 or 5 to LLM.
Thus, improved the context.
![[Pasted image 20261020184552.png]]
for our example ![[Pasted image 20261020184627.png]]
important document(damage policy) got better ranking.

> [!Notes]
> Ranking model work differently than embedding model.
> Embedding model can do similarity of vectors and do embedding of documents and query independently
> it 2 things(raw context) and find relevance score(usefulness of a context for our query) => this are different model(can also be done by LLM model or specialized mode like cross encoder model)

![[Pasted image 20261020185003.png]]
re-ranking should be done only when have many document(big/large scale application).
for smaller documents it is waste of compute and time.
again, trade off between quality and time.
