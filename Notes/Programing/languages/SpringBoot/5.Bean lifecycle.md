It will be explaining how IOC container handles objects/beans.
- create beans
- manage beans
- destroy bean(GC)
### Singleton beans
life cycle :
1. IOC container starts
2. read configuration file(`AppConfig` is also a bean)
3. call @Bean methods in config and manages object return by it.
4. read bean definition(meta data information) like name it is same as class name but 1st letter small.
5. creation of bean dependency on it's scope => instantiate objects and if constructor injection then will happen with creation
6. dependency injection(other ways)
7. Call all Aware interfaces
8. Initialization step(callbacks)
9. Destruction step(callbacks)
10. bean gets destroy after context is closed
There is `Aware` interface => give info about bean and container.
example:
```java
@Component
public class UserService implements BeanNameAware{
    @Override
    public void setBeanName(String name) {
        System.out.println("Bean name is "+name);
    }
    public UserService(){
        System.out.println("UserService created");
    }
}

// main
public class App {
    public static void main( String[] args ) {
        ApplicationContext context=new AnnotationConfigApplicationContext(AppConfig.class);
    }
}
```
gives output as
```bash
UserService created 
Bean name is userService
```
this method of aware interface are called by spring. 
this method are called callback method(called by spring).
if it gives bean name then, why called set beans name??
- it is called by spring => it is callback thus spring gives us the settled name for this bean.
- thus, it can't be used to set bean name.
```java
public class App {
    public static void main( String[] args ) {
        ApplicationContext context=new AnnotationConfigApplicationContext(AppConfig.class);
        UserService us=context.getBean(UserService.class);
        us.setBeanName("Menwo"); // not set Bean Name
        us=context.getBean(UserService.class); 
    }
}
```
it will not change the name.
- can't do any changes in bean by calling callback methods.

#### destruction callbacks
it is to say call method before destroy of bean.similarly,
- `InitializingBean` -> `DisposableBean`(destroy method)
- `init method` -> `destroy method`
- `Post construct` -> `pre destroy`
what have to do in destruction callback
- clear the map
```java
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class App {
    public static void main( String[] args ) {
        ConfigurableApplicationContext context=new AnnotationConfigApplicationContext(AppConfig.class);
        context.close(); // destroy all the beans
    }
}
```
example
```java

	return new CartService();
}
```

### For lazy beans
same will make till bean definition.
and object instances will happen when someone needs it.
and then, injection -> aware -> initialize -> bean ready -> destroy.
### Prototype beans
this are lazy -> goes till definition at start.
will give new object every time => thus will not handle fully
will do on requirement, injection -> aware -> initialization callback -> bean is hand over to client.
now, it will become object outside IOC container and user need to handle.
prototype don't have pre destroy.
why this 
- to avoid memory leak(IOC will become to heavy)=> GC will not be able to clear it if managed by IOC.
also `Context.close()` will not destroy prototype beans.
thus, have try with resources.
#### Circular dependency
resolve circular dependency using post construct also.
instead of constructor injection do post construct injection which will solve circular dependency.
```java
package sachin.yadav;

import org.springframework.stereotype.Component;

import jakarta.annotation.PostConstruct;

@Component
public class A {

    B b;
    public A(B b){
        this.b=b;
    }
    @PostConstruct
    public void setB(){
        b.setA(this);
    }
}
```
for b
```java
package sachin.yadav;

public class B {
    A a;
    public void setA(A a) {
        this.a = a;
    }
}
```
