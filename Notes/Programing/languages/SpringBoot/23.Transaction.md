It brings ACID(Atomicity consistency isolation durability) property to SQL DB.
#### Atomicity
smallest unit of operation which can't be divided further.
it is completed full or none.
#### Consistency
Any transaction on DB will take the DB from 1 valid state to other valid state.(like -ve balance not allowed, conservation of money in transaction).
#### Isolation
concurrent transaction -> many transaction run on same table row.![[Pasted image 20260826101459.png]]
T1 and T2 -> will run in isolation that is one at a time to avoid race condition.
T1 and T2 -> will run isolatedly can't see in middel of working of each other will only see final state of produced by the other transcation.
#### Durable
one transaction sucessfull it should be able to rersist the data.
committed operation should be as it is not effected by future failures.
ACID and transactions are properties of SQL DB.
at spring boot we will use it -> 
- physical transaction: it is done at DB level.
- virtual transaction: it is done at spring app level.

## Isolation levels
It works when concurrency transaction
it is used to solve problems of :-
- Dirty read -> if come data is flushed but not commited that may be read by other transaction then, it might get rollback. change ![[Pasted image 20260829093029.png]] flush ![[Pasted image 20260829093044.png]] dirty read ![[Pasted image 20260829093057.png]] rollback ![[Pasted image 20260829093109.png]] This is called dirty ready ![[Pasted image 20260829093134.png]]
- Non-repeatable reads -> read same row multiple time but get different value at each read.![[Pasted image 20260829094137.png]]![[Pasted image 20260829094152.png]]
problem is when someone commit need to read again to look for change. -> it will not create inconsitence so not a big problem.
- Phantom read -> example query trasaction(t1) ![[Pasted image 20260829094656.png]], if a transaction(t2) insert a query which will add 1 employee in it and commit it.now t1 execute it again and will get 1 more row. -> This is phantom read when doing same bulk query more than once will bring different number of bulk elements.
It is differnt from non-repeatable read as count changes instead of value change.
##### isolation levels
![[Pasted image 20260829101047.png]]
some problem digestable by it -> trade off between concurrency and consistency.
- `READ_UNCOMMITTED` -> all 3 problems(dirty read,non-repeatable read, phantom read) can come, it is weakes isolation and most concurreny.
- `READ_COMMITTED` -> it will avoid dirty read, but still have non-repeatable read and phantom read.
- `REPEATABLE_READ` -> it will prevent dirty read and non-repeatable read but still have phantom read
- `SERIALIZABLE` -> solves all problem but it is not concurrent it is serialized(not always).
![[Pasted image 20260829102452.png]]
need to take a trade off between concurrency and consistency.
generally, preffered is `READ_COMMITTED` and `REPEATABLE_READ`.
- `DEFAULT` -> it depends on DB isolation, for MySQL it is `REPEATABLE_READ` is default.
