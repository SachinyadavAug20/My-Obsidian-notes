## JAR files
traditional flow of java apps
```bash
Demo.java -> compiler -> Demo.class -> any JVM can run
```
- if have many file they will have many .class file to handle which to run when.
- will make a mess
- no standard structure.
to solve this problem has JAR(java archives) => this is package to store .class files, resources, folder etc.
thus, can directly share JAR file.
Library/Dependencies => (has functionality but not runnable)
Application =>  (has library and logic of there use to make it runnable)
Advantages of JAR
- To share java code easily
example can make calculator library `calculator.jar` can be share, with other to be use in there application.
- to use externally libraries => i.e connector for DB(e.g `mysql-connector.jar`)
> [!note]
> If make a library then, jar of dependencies will not be in final jar. has special file which tell which dependencies are need like `Package.json`.
if make a application then, it is a executable JAR thus, will have JAR of all dependencies present in it.
- Java Code + 3rd party libraries(JAR has compiled code) --> compile -> run.
- class path -> to use library .class files

## Life cycle 
Phase between code -> product![[Pasted image 20260704152207.png]]
maven handle project in entire life cycle 
- clean lifecycle
	- clean(clean all old builds (target file) only in current folder)
- Default lifecycle
	- validate -> compile -> test(run test case) -> package(make JAR) -> verify(auth quality check/integration check add plugins like `linter`) -> install(JAR is installed to local(`.m2`) file) -> deploy(goes to remote repository upload only JAR)
- site lifecycle
	- site(documentation and report)
if can run any lifecycle => can't run part of it. either run full lifecycle else none.
e.g like if -> compile => will do validate then compile and stop.
```bash
mvn compile
mvn clean
```
can join command to do in order(very used)
```bash
mvn clean install
```
