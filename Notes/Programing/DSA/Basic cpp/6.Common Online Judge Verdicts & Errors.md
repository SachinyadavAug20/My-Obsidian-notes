## 1. Primary Evaluation Verdicts

- **Accepted (AC):** Your code compiled successfully, ran within limits, and generated the correct output for all hidden test cases.
    
- **Partially Accepted:** Your code works for smaller constraints but fails or runs out of bounds on tougher test data sub-tasks.
    
- **Compilation Error (CE):** Code fails to build due to basic syntax mistakes.

## 2. Compilation Time vs. Execution Time

Understanding the exact sequence of your program's execution pipeline helps you debug errors much faster:

```cpp
chronology
    title The Program Lifecycle
    section Compilation Stage
        Source Code (a.cpp) : 0
        Compiler (gcc) processes headers : 2
        Executable Output (a.out generated) : 4
    section Execution Stage
        System feeds Hidden Input Files : 6
        Program Executes logic steps : 8
        System validates Final Output : 10
```
### The Header Files Fact (`<bits/stdc++.h>`)

- Since `<bits/stdc++.h>` literally pulls in every single standard C++ library at once, it forces the compiler to process significantly more raw code text.
    
- **The Impact:** This directly increases your **Compilation Time**. However, online judges only evaluate resource limits on your **Execution Time**. Compilation time has no impact on performance metrics, meaning you can safely use it without hurting your runtime constraints.

## 3. Detailed Error Breakdowns

### 1. Memory Limit Exceeded (MLE)

- **The Cause:** Your program attempts to reserve more operational RAM than the online platform allows (e.g., trying to allocate more than a specified cap like `256 MB`).
    
- **Common Trap:** Declaring an overly massive array like `int arr[100000000];` ($10^8$ integers $\approx 400\text{ MB}$) inside your solution script.
    
- _Note:_ This oversized block might completely bypass runtime errors on your local computer because desktop systems leverage extended swap memory spaces, but it will fail on an online platform.
    

### 2. Runtime Error (RE)

The program crashes mid-execution due to invalid hardware commands or illegal operations.

- **Illegal Memory Access:** Attempting to read or write to an invalid array index or dereferencing a dangling tracking pointer. On local environments, this triggers a **Segmentation Fault** or a **Core Dump**.
    
- **Undefined Behavior Calculations:** Forcing the CPU to compute an impossible mathematical operation, most notably **Division by Zero** (e.g., `int a = 4 / 0;`).
    

### 3. Time Limit Exceeded (TLE)

- **The Cause:** Your code is too slow and fails to complete processing within the specific runtime limit (typically bound to exactly **1 second** per input tracking file).
    
- **The Golden Metric:** A typical online judge CPU can execute roughly $10^8$ operations per second. If your algorithm requires $10^9$ loops or nested tracking passes, it cannot finish within a 1-second limit.
    

## 4. Special Case: TLE vs. RE in Recursion

When implementing recursive functions without proper terminating criteria, your program can trigger two distinct failure pathways depending on structural boundaries.

```cpp
void function() {
    function(); // Infinite recursion without a base case break condition
}
```

```cpp
block-beta
    columns 1
    space
    block:stack:1
        columns 1
        f3["function() - Layer 3"]
        f2["function() - Layer 2"]
        f1["function() - Layer 1"]
        f0["function() - Layer 0"]
    end
    space
    Overflow_Trigger[["🛑 Stack Memory Limit Exceeded (Crash!)"]]
    stack --> Overflow_Trigger
```

### Path A: Runtime Error via Stack Overflow (Most Common)

Every consecutive function invocation allocates a brand-new tracking record frame inside the application's internal memory **Stack**. If the logic loops indefinitely with no base case, the stack runs out of memory and crashes instantly. Because this memory exhaustion halts execution completely, it registers immediately as a **Runtime Error (RE)** long before the 1-second time limit clock can run out.

### Path B: Time Limit Exceeded (TLE)

If your recursive function _does_ have a proper base case that avoids stack exhaustion, but the calculation branches out inefficiently (like an un-optimized $O(2^n)$ Fibonacci calculation), it will exhaust the 1-second time allowance, resulting in a **Time Limit Exceeded (TLE)** verdict.
