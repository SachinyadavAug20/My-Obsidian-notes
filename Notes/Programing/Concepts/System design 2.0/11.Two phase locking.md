## 2 phase locking
it is a way to achieve isolation/serialize-ability.
[[10.Actual serial execution(e.g Volt DB)]] => run actually on 1 thread.
here, make concurrent transaction seem as if they were running on 1 thread.
done using locking => seen in tradition DB.
![[Pasted image 20261111205103.png]]
instead of lock giving exclusive look have 2 looks
1. Read lock
2. Write lock
![[Pasted image 20261111213634.png]]
while reading => grab reader lock
while writing => grab writer lock
so, at a time only 1 reader and 1 writer.
for read -> modify -> update cycle => Sol: when reading will not allow to write also
that is writer lock is exclusive 1 row has 1 writer lock and nothing else(no reader)
for reader there can be many readers
#### Problem
Deadlocks
![[Pasted image 20261111214453.png]]
both user see each other cart and try to add those item in there cart.
1. Both locked for reading for their and other person's cart(as multiple reader allowed) ![[Pasted image 20261111214707.png]]
2. try to get writer for self cart => but as reader lock is applied writer lock can't be taken as it is exclusive => thus none of them leave reader and both try to get writer 
   ![[Pasted image 20261111215131.png]]
Two phase locking is slow
- too many deadlocks(system has to detect them and abort them)
- Also have phantoms
![[Pasted image 20261111215703.png]]
In read -> modify -> update(add new row)
![[Pasted image 20261111215819.png]] both write join a class with enrollment capacity of 3.
because can't lock row that don't exist yet.
#### Solve
Predicate(make row in advance and apply lock to all slots) locks:
![[Pasted image 20261111215954.png]]
lock all rows and thus, maintain invariance of only 3 capacity.
if no indexing for this query then, will be very slow.
solve: using index range locking
