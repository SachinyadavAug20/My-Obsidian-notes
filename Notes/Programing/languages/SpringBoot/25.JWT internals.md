@RestController
@RequestMapping("/api/user")
public class UserController {
    private AuthService authService;

    public UserController(AuthService authService) {
        this.authService = authService;
    }

    @GetMapping("/hello")
    public ResponseEntity<String> sayHello(Authentication authentication) {
        return ResponseEntity.ok("Hello, you are logged in as " + authentication.getName());
    }

    @PostMapping("/register")
    public ResponseEntity<UserRegisterResponseDto> register(
            @RequestBody UserRegisterRequestDto userRegisterRequestDto) {
        return ResponseEntity.ok(authService.registerUser(userRegisterRequestDto));
    }

    @GetMapping("/token")
    public CsrfToken getToken(CsrfToken csrfToken) {
        return csrfToken;
    }
}

```java
        httpSecurity.csrf(csrf->csrf.disable())
            .authenticationProvider(authenticationProvider)
            .formLogin(Customizer.withDefaults())
            .httpBasic(Customizer.withDefaults())
            .authorizeHttpRequests(auth->
                        auth.requestMatchers("/register").permitAll() // allowed no login required
                        .requestMatchers("/admin/**").hasRole("ADMIN")
                        .anyRequest().authenticated()
            )
            .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.IF_REQUIRED));
```
Session creation policy has 4 enums
- `ALWAYS` -> always create session Id
- `NEVER` -> destroy the Authentication object and id is never create it.
- `IF_REQUIRED` -> default, create session Id if needed
- `STATELESS` -> used for JWT.
Problem: sticky session(State-full problem) 
- will store session mapping(`sessionId`:``Authentication``) on server which will create problem in distributed multiple servers.
thus, can use state-less architecture.
##### State-less architecture
first request will always redirect to `/login`.
server will create the authentication object after login ![[Pasted image 20260913113325.png]]
will not store the authentication object as it is state-less.
server will give a token(JWT-token) which will be stored in cookies.
on any new request, server can rebuild the authentication object again by using the token.
token is full self contained so can make full authentication object using it.
![[Pasted image 20260913113728.png]]
## JWT-token
JWT -> JSON web token.
this is special web-token which contain all information to create an authentication object.
Signed JWT provides integrity and authenticity.(that is it is secure).
![[Pasted image 20260913115217.png]]
store sufficient information to make the authentication object in JWT-token.
no need to pass credentials.
JSON to string token is send.
string converted to JSON using `Base64URL`.
process -> make `Base64URL`(URL friendly string 2 way not hashing) of any object and then can use than URL/string to make that object back. -> only encoding not encrypting.
#### Problems
- server trusting a string. 
- if client changes that string and try to get other people account by using hit and try(as client also know how to convert token -> JSON)![[Pasted image 20260913120205.png]] user can make himself admin. -> change token and trick server.
server should not believe the client and versify it's clams.
now, instead of encoding do hashing(because it is one way).
