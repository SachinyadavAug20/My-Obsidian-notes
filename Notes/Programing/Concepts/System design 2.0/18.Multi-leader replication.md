## Multi-leader replication
used for more write throughput => as now more leader thus, more place to write things to.
![[Pasted image 20261118171029.png]]
made leader for each region
anyone can write to any leader and can read only from the followers.
leaders also pass writes to each other for replication.
There are different configuration to pass this writes called as topologies
## Topology
### Circular topology
![[Pasted image 20261118171924.png]]
all leader in circle => if a node is killed then problem.
![[Pasted image 20261118171955.png]]
problem due to circular dependency => inconsistency propagation.
### Star topology
![[Pasted image 20261118172247.png]]
all pass writes to center of star and that leader of leader pass to all other leaders.
killing nodes(leader) won't affect stop propagation of write, it will just slow down.
if center/leader of leaders is killed will have problems
Problem : single point of failure.
### All to all topology
![[Pasted image 20261118172550.png]]
everyone knows every other leader and asks for updates independently.
any single node goes down => no problem.
Problem: causality(order of writes confusion) => ![[Pasted image 20261118172747.png]]
This is fixable but, add complexity.
## Replication log

## Write conflicts
![[Pasted image 20261118173555.png]]
both leader updated same field with different value now, whose data to keep and whose to discard.
like race condition due to concurrent writes are possible.
#### Easy Solution 
=> all writes to the same key goes to same replica.
problem : far away people need to write to same replica takes longer.
#### Last write wins
as each write has timestamp take the latest data.
![[Pasted image 20261118174009.png]]
problem : whose timestamp to us ??
1. sender(user)
